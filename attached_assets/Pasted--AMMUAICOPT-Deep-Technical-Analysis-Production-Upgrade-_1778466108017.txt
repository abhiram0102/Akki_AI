## STEP 2 — ENGINEERING WEAKNESS ANALYSIS

### W-01: Dual Runtime Fragmentation (CRITICAL)
**What:** Two completely separate AI backends exist — a TypeScript/Node.js backend (`server/services/ai.ts`) and a Python backend (`backend/services/ai_service.py`) — both calling Gemini, both defining agent personas, both implementing routing logic, with **no shared state or IPC**.

**Why it matters:** Every feature implemented in one runtime must be duplicated in the other. The Python backend uses Gemini 2.0 Flash with 7 richly-defined agent personas (NEXUS, GHOST, PHANTOM, SENTINEL, DISSECT, MENTOR, ARCHIVE). The TypeScript backend uses Gemini 1.5 Pro with a simpler wrapper. These two systems are siloed; the frontend hits whichever one is actually wired up, leaving half the capability dead weight. This is not a monorepo multi-service design; it is accidental duplication without a service boundary contract.

### W-02: In-Memory Workflow State (CRITICAL)
**What:** `AgentOrchestrator` stores all active executions in a `Map<string, WorkflowExecution>` in process memory. `agents`, `workflows`, and `activeExecutions` are instance fields with no persistence.

**Why it matters:** Any server restart (Replit cold start, deploy, crash) destroys all running workflows. No user can safely initiate a long-running pentest workflow — it will silently evaporate. There is also no horizontal scaling: a second process instance has zero knowledge of the first's executions. `pauseWorkflow` sets a flag but does NOT actually interrupt in-flight Promises. `resumeWorkflow` changes the status back to "running" but never re-invokes execution logic. The pause/resume API is **entirely non-functional**.

### W-03: JWT Re-Validated Against Database on Every Request (HIGH)
**What:** `authMiddleware` calls `storage.getUser(decoded.userId)` — a full PostgreSQL round-trip — for every authenticated API call.

**Why it matters:** At 100 concurrent users each making 10 req/s, this generates 1000 DB queries/s just for auth. Neon serverless PostgreSQL has cold-start latency of 500ms+. A simple Redis/in-memory token cache with a 5-minute TTL would cut this to zero DB calls for the vast majority of requests.

### W-04: Simulated Streaming (HIGH)
**What:** `stream_completion` in Python's `ai_service.py` fetches the entire response from Gemini, then yields it word-by-word with `asyncio.sleep(0.02)`. This fakes streaming.

**Why it matters:** The user perceives the illusion of streaming but the actual latency until first token equals full Gemini inference time (~2-8 seconds for long responses). True streaming via Gemini's `generate_content_stream` would deliver first token in ~200-500ms, dramatically improving perceived responsiveness for a tool used by security analysts under time pressure.

### W-05: Naïve Text Chunking (HIGH)
**What:** `ragService.chunkText()` splits text at fixed character offsets (1000 chars, 200 overlap), with a weak heuristic to break at the last `.` or `\n` found after 70% of chunk length.

**Why it matters:** Security documents (CVE advisories, pentest reports, MITRE ATT&CK pages) have structured sections. Character-level chunking splits MITRE technique tables mid-row, CVE descriptions mid-sentence, and code blocks mid-function. This directly degrades RAG retrieval quality, causing incorrect or incomplete answers when analysts query their uploaded documents.

### W-06: Embedding Model Mismatch / Dimension Corruption Risk (HIGH)
**What:** `generateEmbedding` uses Gemini `embedding-001` (768-dim). PostgreSQL stores embeddings as `real[]` (flat float array). ChromaDB receives the same embedding. There is no dimension validation, no versioning, and no migration path if the embedding model changes.

**Why it matters:** If Gemini deprecates `embedding-001` (already happened — it's superseded by `text-embedding-004`), all stored embeddings become stale. New documents would embed into a different vector space, making cosine similarity between old and new chunks meaningless. There is no guard against this silent corruption.

### W-07: ChromaDB as External Hard Dependency with Fragile Fallback (HIGH)
**What:** RAG initializes by connecting to `http://localhost:8000`. On failure, it sets `chromaAvailable = false` and falls back to direct AI response. This flag is module-level, so a one-time initialization failure permanently disables RAG for the process lifetime.

**Why it matters:** On Replit free tier, ChromaDB as a localhost service requires a separate Replit repl or process. If the Chroma process isn't running when the Node process starts, RAG is silently dead for the entire server session — no retry, no health check loop, no alerting to the user.

### W-08: Agent Orchestrator Ignores Phase Dependencies (MEDIUM-HIGH)
**What:** `executePhase()` iterates `workflow.phases` sequentially using a simple `for...of` loop. The `dependencies` field on each phase is populated but **never checked or enforced**. If phase B declares `dependencies: ["phase-a"]`, the orchestrator will still attempt to run it even if phase A failed or was skipped.

**Why it matters:** Multi-phase pentest workflows require strict dependency ordering (you cannot do exploitation analysis before recon completes). Currently if the recon phase throws, the loop catches the error and marks the whole workflow `failed`, but it has already tried (and failed) to pass empty recon results downstream. Phase results accumulate via `prepareTaskParameters` which blindly passes whatever is in `execution.results`, including empty failed results.

### W-09: Hardcoded Fallback JWT Secret (CRITICAL SECURITY)
**What:** `const JWT_SECRET = process.env.JWT_SECRET || "your-secret-key"`. If the env var is unset (common in Replit), all JWTs are signed with the publicly known string `"your-secret-key"`.

**Why it matters:** Any attacker who reads this code (it's in a public Replit) can forge arbitrary JWTs and authenticate as any user, including admins. This is a complete authentication bypass.

### W-10: Passwords Hashed with bcrypt Cost Factor 12 Without Async Rate Limiting (MEDIUM)
**What:** `bcrypt.hash(data.password, 12)` on the Express route. Cost factor 12 = ~300ms per hash on modern hardware. No rate limiting on `/api/auth/register` or `/api/auth/login`.

**Why it matters:** bcrypt is correct. But without rate limiting, an attacker can flood the registration endpoint to consume all Node.js event loop time with CPU-bound bcrypt operations, causing a DoS on the entire API server (Node.js is single-threaded for sync operations; bcrypt blocks the event loop when not using worker threads properly).

### W-11: No Request Size / Rate Limiting (HIGH)
**What:** Multer allows 50MB uploads. No rate limiting middleware is applied (helmet is imported but rate-limit is not). No body size restriction on JSON routes.

**Why it matters:** A malicious or careless user can post 50MB JSON bodies to the chat endpoint, triggering a 50MB Gemini API call that runs for seconds and costs money. Without rate limiting, the Gemini API key can be drained to zero quota.

### W-12: Conversation History Truncation at 10 Messages (MEDIUM)
**What:** Python's `ai_service.py` truncates to `messages[-10:]` before sending to Gemini. No summarization, no semantic compression.

**Why it matters:** A pentest session typically involves 50-100 messages. Truncating to 10 means the AI loses all context from the beginning of the engagement — earlier recon findings, agreed-upon scope, target details — causing it to hallucinate or ask for information already provided. This is especially damaging for multi-phase agent workflows spanning dozens of turns.

### W-13: Emotional Bond State as JSONB in PostgreSQL (LOW-MEDIUM)
**What:** `emotionalState: jsonb` on the `users` table, updated on every interaction via `updateUserEmotionalState`. Bond level is a single integer 0-100 incremented in application logic.

**Why it matters:** No atomic increment (race condition with concurrent sessions). No bounds validation in the DB layer (nothing prevents bond_level = 9999). The "emotional AI" is purely cosmetic prompt engineering with no real behavioral branching tested.

## STEP 3 — AI / MODEL ANALYSIS

### M-01: Single LLM Provider Lock-In (Gemini Only)
The entire system is hard-wired to Google Gemini (`gemini-1.5-pro-latest` in TS, `gemini-2.0-flash` in Python). No fallback to Anthropic Claude, OpenAI GPT-4o, or local models. If Google raises API pricing, changes model behavior, or has an outage, the entire product goes down. The `openai` npm package is listed in `package.json` but is completely unused.

**Recommendation:** Implement an LLM abstraction layer (`LLMGateway`) with provider-specific adapters (Gemini, OpenAI, Anthropic, Ollama/local). Route based on task type: cheap tasks → Flash; complex reasoning → Pro/Claude Opus; offline/sensitive → local Llama.

### M-02: No System Prompt Caching
Every Gemini call reconstructs the full system prompt from scratch and sends it as part of the `history`. Gemini supports explicit `systemInstruction` but the Python backend concatenates it into the conversation string manually, causing it to be re-encoded and billed as input tokens on every call.

**Recommendation:** Use Gemini's native `systemInstruction` field (TypeScript backend already does this correctly). In the Python backend, pass `system_instruction` as a separate `GenerateContentConfig` field. Consider Gemini's Context Caching API for static system prompts (up to 75% cost reduction).

### M-03: JSON Mode Without Schema Enforcement
`jsonMode: true` asks the model to return JSON but provides no JSON schema. The model can and does return structurally variable JSON. The TypeScript backend parses and validates with Zod only in `generateCybersecurityResponse`. Other methods (`generateExploitPoC`, `generateOSINTStrategy`, `planCustomWorkflow`) use raw `JSON.parse()` without validation.

**Recommendation:** Use Gemini's `responseSchema` parameter (available in Gemini 1.5 Pro and 2.0+) to enforce exact JSON structure. This eliminates parsing errors, reduces hallucinated keys, and removes the need for defensive Zod checks after parsing.

### M-04: Temperature Values Not Calibrated to Task
- `planCustomWorkflow`: temperature=0.4 (reasonable for structured output)
- `generateEmotionalResponse`: temperature=0.8 (too high — produces inconsistent persona behavior)
- `route_to_agent`: temperature=0.1 (correct for classification)
- `stream_completion` (general chat): temperature=0.7 (too high for security-critical technical responses)

**Recommendation:** Security technical responses should use temperature 0.2-0.4. Higher temperatures increase hallucination of CVE IDs, MITRE technique numbers, and tool syntax — catastrophic in a cybersecurity context where a fabricated CVE or wrong exploit code could guide an analyst incorrectly.

### M-05: No Grounding, Citation, or Hallucination Detection
The AI freely generates MITRE ATT&CK IDs, CVE numbers, tool names, and exploit code. There is no verification layer. The `mitreTags` array in responses is LLM-generated — the model will confidently produce `T1599.001` (a real technique) in a context where `T1190` (a different technique) is actually relevant.

**Recommendation:** Implement post-generation validation: (1) regex-extract all T-codes and CVE-IDs from responses; (2) validate against a local copy of the MITRE ATT&CK STIX dataset and NVD CVE feed; (3) flag or reject responses with invalid IDs before returning to user.

### M-06: RAG Retrieval Quality Issues
- Cosine distance on `embedding-001` embeddings is used without MMR (Maximum Marginal Relevance) — results can be redundant
- No reranking (cross-encoder) step after initial retrieval
- `topK=5` is fixed, not adaptive to query complexity
- `calculateConfidence` is a simplistic average with a source-count penalty — not calibrated

**Recommendation:** Add a cross-encoder reranker (`ms-marco-MiniLM-L-6-v2` via a Python sidecar) after initial retrieval. Apply MMR with lambda=0.7 to balance relevance and diversity. Implement adaptive `topK` based on query length and type (simple factual → 3, complex multi-hop → 10).

## STEP 4 — DATASET & DATA PIPELINE ANALYSIS

### D-01: No Security Corpus Pre-Loading
The RAG system starts empty. Users must upload documents manually. There is no pre-ingested knowledge base with MITRE ATT&CK, CVE data, OWASP, exploit databases, or security tool documentation.

**Recommendation:** Pre-ingest the following on first launch:
- Full MITRE ATT&CK Enterprise matrix (JSON from GitHub: `mitre-attack/attack-stix-data`)
- OWASP Testing Guide and Top 10 documentation
- SANS reading room papers (openly licensed)
- Tool manpages (nmap, metasploit, sqlmap, etc.) as structured markdown
- NVD CVE feed (last 3 years, ~50GB compressed — chunk by CVE ID)

### D-02: Document Store Without Deduplication
`ingestDocument` creates a new document record and chunks without checking if the same file content already exists. A user re-uploading the same CVE advisory creates duplicate embeddings in ChromaDB, polluting retrieval with redundant chunks that reduce diversity.

**Recommendation:** Compute SHA-256 of file content before ingestion. Check against a `content_hash` column in the `documents` table. On collision, skip ingestion and return the existing document ID.

### D-03: No Support for Structured Security Data Formats
The ingestor handles PDF, text, and markdown but not: STIX/TAXII bundles, SARIF (vulnerability scan output), OpenVAS/Nessus XML, Burp Suite state files, Nmap XML output, or CSV/JSON tool outputs. Security analysts generate these formats constantly.

**Recommendation:** Add format-specific parsers for each: STIX 2.1 → extract Objects and Relationships; Nmap XML → extract host/port/service/script trees as structured text; SARIF → extract rule IDs, locations, and messages; Nessus XML → extract finding blocks per plugin.

### U-03: Cross-Encoder Reranking for RAG

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

async def reranked_retrieve(query: str, top_k: int = 5) -> list[dict]:
    # First pass: vector search (fast, coarse)
    candidates = await chroma.query(query_embedding, n_results=20)
    
    # Second pass: cross-encoder reranking (slow, precise)
    pairs = [(query, c["content"]) for c in candidates]
    scores = reranker.predict(pairs)
    
    reranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
    return [item for item, score in reranked[:top_k]]
```

## STEP 7 — RELIABILITY & TRUSTWORTHINESS

### R-01: Confidence Calibration System

```python
class ResponseConfidenceScorer:
    def score(self, response: dict, query: str, rag_sources: list) -> float:
        scores = []
        
        # Check MITRE ID validity
        for tag in response.get("mitreTags", []):
            scores.append(1.0 if self.is_valid_mitre_id(tag) else 0.0)
        
        # Check CVE ID format validity
        cve_ids = re.findall(r'CVE-\d{4}-\d+', response.get("content", ""))
        for cve_id in cve_ids:
            scores.append(1.0 if self.is_valid_cve(cve_id) else 0.0)
        
        # RAG source coverage
        if rag_sources:
            coverage = len([s for s in rag_sources if s["relevanceScore"] > 0.75]) / len(rag_sources)
            scores.append(coverage)
        
        return sum(scores) / max(len(scores), 1)
```

Display confidence scores to the analyst so they know when to verify AI output independently.

### R-03: Tool Execution Sandboxing

The `toolRuns` table has an `approvalRequired` flag but the actual tool execution in `tools.ts` is not sandboxed. Security tools (nmap, sqlmap, metasploit) should only execute:
- Against targets explicitly in an approved scope list
- In a containerized environment (Docker with network isolation)
- With time limits (max 5 minutes per tool run)
- With output size limits (max 10MB returned)

```python
class SandboxedToolExecutor:
    async def execute(self, tool_name: str, args: dict, scope: list[str]) -> dict:
        target = args.get("target", "")
        if not self.is_in_scope(target, scope):
            raise ScopeViolationError(f"Target {target} not in authorized scope: {scope}")
        
        container = await docker_client.containers.run(
            image=f"ammu-tools:{tool_name}",
            command=self.build_command(tool_name, args),
            network="isolated_pentest_net",
            timeout=300,
            mem_limit="512m",
            remove=True
        )
        return {"output": container.logs().decode(), "exit_code": container.wait()["StatusCode"]}
```

## STEP 8 — PERFORMANCE OPTIMIZATION

### P-01: Batch Embedding API Calls

Current: 1 Gemini embedding API call per chunk = O(n) API calls for n-chunk document.
Upgraded: Batch embeddings in groups of 100 (Gemini's `batch_embed_contents` endpoint):

```python
async def embed_batch(texts: list[str], batch_size: int = 100) -> list[list[float]]:
    all_embeddings = []
    for i in range(0, len(texts), batch_size):
        batch = texts[i:i+batch_size]
        result = await client.models.batch_embed_contents(
            model="text-embedding-004",
            contents=[types.Content(parts=[types.Part(text=t)]) for t in batch]
        )
        all_embeddings.extend([e.values for e in result.embeddings])
    return all_embeddings
```

Result: 100x fewer API calls for document ingestion, proportionally lower latency and cost.

### P-02: PostgreSQL pgvector Instead of ChromaDB

```sql
CREATE EXTENSION vector;

CREATE INDEX ON chunks USING ivfflat (embedding_v2 vector_cosine_ops) WITH (lists = 100);
```

```python
async def vector_search(query_embedding: list[float], top_k: int = 5):
    return await db.execute("""
        SELECT id, content, metadata,
               1 - (embedding_v2 <=> $1::vector) AS similarity
        FROM chunks
        ORDER BY embedding_v2 <=> $1::vector
        LIMIT $2
    """, [query_embedding, top_k])
```

Benefits: single service (PostgreSQL), ACID-consistent with document records, no localhost ChromaDB requirement, Neon supports pgvector.

## STEP 11 — SECURITY & SAFETY ANALYSIS

### S-01: Hardcoded Google API Key in `.env.example` (CRITICAL)
**Finding:** `.env.example` contains `GOOGLE_API_KEY="AIzaSyDpLbmD4ZWDBkWegxLxPJny5dCBX9LU0NQ"`. This appears to be a real API key committed to version control (the file is in the zip archive which was committed to git). If this key is real and valid, it is already compromised.

**Action:** Immediately rotate this key in Google Cloud Console. Never commit real keys to any file under version control, even example files.

### S-02: Exploit Generation Without Authorization Verification
`generateExploitPoC` and `generate_exploit` in both backends will generate working exploit code for any vulnerability with no verification that the requesting user has authorization to test the target. The "ethical guidelines" in the system prompt are purely advisory — a determined user can bypass them with prompt engineering.

**Mitigation:** Add an explicit "authorized target declaration" step: before generating exploit code, require the user to confirm a scope document, store the confirmation with timestamp and user ID in the audit log. Display a legal disclaimer. This does not prevent misuse but creates accountability.

### S-03: SSRF Risk via Tool Execution
If the `tools.ts` service can be instructed to make network requests (e.g., `web_fetch`, `http_probe` tools) based on user-provided URLs without validation, this creates Server-Side Request Forgery. An attacker could exfiltrate internal AWS metadata (`169.254.169.254`) or Neon database credentials.

**Mitigation:** Implement an allowlist/denylist for tool target URLs. Deny RFC-1918 ranges, link-local addresses, and cloud metadata endpoints.

### S-04: No Input Sanitization for Code Analysis
`analyze_code` in Python passes up to 3000 characters of user-provided code directly into the Gemini prompt. While Gemini has its own safety filters, a carefully crafted input could use the code analysis context to extract system prompt details or manipulate the AI's response.

**Mitigation:** Strip or escape special characters that could act as prompt delimiters. Wrap user code in explicit XML-like markers: `<user_code>...{code}...</user_code>`.

### S-05: Session Tokens in URL Parameters (If Present)
Review the client-side API calls in `client/src/lib/api.ts` to ensure JWTs are only sent in Authorization headers, never as query parameters (which would appear in server access logs).
